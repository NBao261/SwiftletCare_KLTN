# backend/CLAUDE.md

Rules and architecture for `backend/` (Node.js + Express + TypeScript + MongoDB + MQTT/EMQX + Socket.io). This file wins over the root `CLAUDE.md` for backend code; `/review-pr` judges backend changes by it. Rule tags: **[Bắt buộc]** = blocking (review requests changes), **[Nên]** = advisory. Only lines a PR adds or changes are judged; the "Known debt" table lists what is already out of line.

Requirements are Report 3 (`docs/reports/report3-srs.md`) and the design is Report 4 (`docs/reports/report4-sdd.md`); they win over `SwiftletCare_SRS.md` and over this file's description of behaviour. The backend follows the Review 1 scope: roles `ADMIN | FARM_OWNER | DOMAIN_EXPERT | TECHNICIAN`, no Marketplace, no heating relay, NH3/CO2 alert-only, `NOISE_ANOMALY` instead of `BIRD_PANIC`, Telegram and FCM push as the out-of-app channels. Where the code still falls short of Report 3, the gap is in `docs/reports/README.md` and in Known debt below.

Dev EMQX self-signs its TLS cert on 8883, which the Node `mqtt` client rejects — dev config must use **`mqtt://localhost:1883`**; `mqtts://...:8883` + a real CA cert only in production. CI (`.github/workflows/ci.yml`, job Backend) runs `npm ci`, `lint`, `build:check` and `npm test` on every PR that touches `backend/` or `docs/api/api-spec.yaml`.

## Architecture: Route → Controller → Service → Model

```
routes/*.route.ts (express-validator + requireRole)
  → controllers/*.controller.ts (parse req, call exactly one service fn, res.json)
      → services/*.service.ts (the only layer that queries DB, checks permissions, publishes MQTT, emits socket events, throws AppError)
          → models/*.model.ts (Mongoose schemas)
```

**Express middleware order** (`config/app.config.ts`): `helmet()` → `cors({origin: CORS_ORIGIN ?? http://localhost:5173, credentials: true})` → `rateLimiter` (`RATE_LIMIT_WINDOW_MS`/`RATE_LIMIT_MAX`, default 100 req/60s) → `morgan('combined')` → `express.json({limit:'10mb'})` → `urlencoded` → `cookieParser()` → `requestContext` (AsyncLocalStorage holding the client IP so `logAction()` can fill `audit_logs.ip_address`; set `TRUST_PROXY=<hops>` behind a proxy, never `true`) → `/health` → `/files` (static, only when `STORAGE_DRIVER=local` — dev stand-in for MinIO) → Swagger (`/api-docs`, spec loaded from `docs/api/api-spec.yaml` in a try/catch — a missing spec only logs a warning) → 12 domain routers + `/internal` (MediaMTX) → 404 handler → `errorHandler` (must stay last). `config/db.config.ts#connectDB()` requires `MONGODB_URI`, `maxPoolSize: 10`.

**Models** (`src/models/*.model.ts`, one per file): `user`, `farm` (+ embedded members; soft-deleted — `utils/softDelete.util.ts#applySoftDeleteScope` hides `is_deleted` docs from every `find*`/`countDocuments` unless the filter names `is_deleted`, same for `harvestBatch`; delete a farm via `farm.service#softDeleteFarm`, which also resolves open alerts and expires pending invitations), `houseZone` (House + Zone, with threshold history, fuzzy-control tuning and detection tuning + their histories, each entry recording the editor's role; House holds `bird_count_tuning` + history), `device` (SensorNode per Zone + CameraNode per House), `audioTrack` (lullaby files per device on MinIO via `config/minio.config.ts`; the real copy lives on the DFPlayer SD card), `telemetry`, `alert`, `auditLog`, `systemSetting` (singleton, unique `_singleton` key), `invitation`, `harvestBatch`, `birdCountRecord` (one row per camera + session + `session_date`, Vietnam date), `birdCountBucket` (5-minute counts, TTL 90 days; VISION-FR-017), `notification` (in-app inbox, TTL 90 days; EXPERT-FR-006/007), `provisionedDevice`, `relayOverrideLog` (one row per manual override — who, role, relay, forced state, start/expiry/end, end reason; ENV-FR-019; written best-effort *after* the relay command is published), `zoneHealthReport` (EXPERT-FR-005/006). No SALES module, no Marketplace (`harvest.service.ts` only records harvests).

**Socket.io** (`src/socket/index.ts`): JWT-authenticated in `io.use` (`socket.handshake.auth.token` vs `JWT_ACCESS_SECRET`). Clients `JOIN_ZONE`/`LEAVE_ZONE` room `zone:${zoneId}` (checked with `assertZoneAccess`), `JOIN_HOUSE`/`LEAVE_HOUSE` room `house:${houseId}` (checked with `assertHouseAccess`; bird counts, bird-counting camera status and house alerts). Services never touch `io` directly — they call `emitTelemetryUpdate`, `emitRelayUpdate`, `emitAlertNew`, `emitDeviceStatusChange` (zone rooms), `emitBirdCountUpdate`, `emitHouseDeviceStatusChange`, `emitHouseAlertNew` (house rooms) and `emitNotificationNew` (`NOTIFICATION_NEW`, room `user:${userId}` joined on connect).

**Alert Engine** (`alert.service.ts`): `createAlert()` is the single entry point. Only HIGH/CRITICAL are sent again when nobody acknowledges them (ALERT-FR-015), so every *inferred* type (`NOISE_ANOMALY`, `SENSOR_ANOMALY`, `FORECAST_BREACH`, `LOW_RETURN_RATE` — `INFERRED_ALERT_TYPES`) stays MEDIUM/LOW; `ingestDeviceAlert` caps those and `THRESHOLD_BREACH` at MEDIUM and maps the old `BIRD_PANIC` name from firmware < 1.3.0; it rejects types only the backend may infer (`NODE_OFFLINE`, `SENSOR_ANOMALY`, `FORECAST_BREACH` — `BACKEND_ONLY_ALERT_TYPES`) when a device sends them. NH3/CO2 breaches are alert-only (ALERT-FR-012). Bird-counting alerts (`EDGE_AI_DEGRADED`, `LOW_RETURN_RATE`) belong to the **house** (`houseId`, no `zoneId`; `GET /alerts?houseId=`). Domain Expert verdicts go through `PUT /alerts/:id/verdict` (`alerts.expert_verdict`, EXPERT-FR-003), separate from `acknowledge` (Farm Owner only, ALERT-FR-009). Dedup per incident: an open (`ACTIVE`/`ACKNOWLEDGED`) alert with the same `farm_id + zone_id + house_id + node_id + type` only bumps `last_seen_at` + `occurrence_count` (at most once a minute) and returns `null`. `NODE_OFFLINE` resolves when the device returns (`device.service.ts#announceBackOnline`, shared by `recordHeartbeat` and `markNodeSeen`). New alerts emit `ALERT_NEW` and fire-and-forget `dispatchAlertNotification()` (`notification.service.ts`: recipients are the farm's owners, not experts; **Telegram** really sends via `telegram.service.ts` — ALERT-FR-013; FCM push only logs; Zalo/SMS out of scope). `notifyUser` also writes the in-app inbox (`notification.service#createInAppNotification`, `GET /notifications`); a new inferred alert notifies the farm's Domain Experts **in-app only** (`dispatchAlertNotification(alert, { awaitsVerdict })`, EXPERT-FR-007 / ALERT-FR-005).

**Bird counting** (`birdCount.service.ts`, `docs/bird-counting-plan.md` §8): Report 3 §2.8 — the camera sits at the entrance of the **whole swiftlet house** (1–2 entrances), so `CameraNode`, `bird_count_records`, `bird_count_buckets` carry `house_id` (no `zone_id`) and every count is per **House**. `houseDailyCounts()` sums the raw counts of every camera of the house per `session_date` and only then takes net counts and the return rate (birds may leave by one entrance and return by another; `null` rate when a session is missing). It is the only source for `GET /analytics/bird-count/current|daily|trends`, `/correlation` (a zone's environment vs its house's return rate), the `BIRD_COUNT_UPDATE` payload (house totals, room `house:<id>`), the house-level `LOW_RETURN_RATE` job (threshold `houses.bird_count_tuning.return_rate_drop_pct`, `PUT /farms/houses/:houseId/bird-count-tuning`, Domain Expert only), health-report `avg_return_rate` and the harvest flock snapshot (a zone reads its house) — never aggregate `bird_count_records` elsewhere. Bird-count endpoints and camera listing/registration still accept the old `zoneId`/`zone_id` and map it to the zone's house (`farmAccess.util#assertHouseAccessByParams`). `vision/bird-count` carries session messages (cumulative per session, upserted on camera + session + `session_date`; no per-camera return rate is stored) and `kind: 'BUCKET'` 5-minute messages (`bird_count_buckets`, `GET /analytics/bird-count/buckets`). Read endpoints group by `session_date` (Vietnam day), never by the UTC day of `timestamp`. The AI node's heartbeat reuses the ESP32 heartbeat topic (`recordHeartbeat` falls back to `CameraNode`; the only config pushed back is the counting ring, when one was drawn) and `vision/alert` only accepts `EDGE_AI_DEGRADED` from a camera; `LOW_RETURN_RATE` is backend-only. `listCameraNodes` never returns `rtsp_url`.

**Live stream** (`stream.service.ts`, plan §8.6/§18.3, VISION-FR-013): video never passes through the backend. `GET /devices/camera-nodes/:id/stream-token` (Farm Owner/Domain Expert only, Report 3 §2.4) (checked on the camera's house) signs a 60-second JWT with `STREAM_TOKEN_SECRET` (never `JWT_ACCESS_SECRET`) for path `cam-<device_id>`. MediaMTX (`deploy/mediamtx.yml`, 1.21.1) calls `POST /internal/stream-auth?key=STREAM_AUTH_KEY` (`routes/internal.route.ts`, no user JWT, blocked from outside by the reverse proxy) on every publish/read: the pipeline publishes and reads the raw `cam-<id>-raw` feed with `STREAM_PUBLISH_SECRET`; viewers read `cam-<id>` with the token (Bearer header → `token`, `?token=`, or password); everything else gets 401. A `device_id` ending in `-raw` gets no token (it would name another camera's raw feed).

**Auth** (`auth.service.ts` + `auth.route.ts`): `register/login/refresh/logout/otp/send/otp/verify/forgot-password/reset-password/notification-preferences/telegram/link/delete-request` (invitation accept/decline in `invitations.route.ts`). Access token: JWT (`JWT_ACCESS_TTL`, default 15m) in the JSON body, checked by `authenticate` and Socket.io. Refresh token (`JWT_REFRESH_TTL`, default 30d): httpOnly cookie (`secure` in prod, `sameSite: 'strict'`) *and* stored in `user.refresh_tokens[]` so it is individually revocable; `/refresh` checks both; `resetPassword` wipes the array. OTP/reset codes are 6-digit and SHA-256-hashed; in dev they are only logged.

**MQTT**: ESP32 topics `swiftletcare/{farmId}/{houseId}/{zoneId}/...`, AI-node (bird-counting camera) topics `swiftletcare/{farmId}/{houseId}/heartbeat|vision/bird-count|vision/alert` (no zone, Report 3 §2.8; `{house}/vision/alert` is caught by the ESP32 `+/+/+/alert` pattern, so no separate subscription — overlapping ones would duplicate deliveries). They use real MongoDB ObjectIds (matters for firmware provisioning). Ingestion keys off `deviceId` inside the JSON payload (`SensorNode.device_id`), not topic segments — topics only drive wildcard subscription (`mqtt/mqtt.client.ts`, `TOPICS`). A manual relay override lasts `MIN_OVERRIDE_MS` (1 min = 2 × `DEVICE_CONFIRM_GRACE_MS`) to `MAX_OVERRIDE_MS` (24 h), default 30 min. Remote `RESTART`/`OTA` return 501 for a device whose `firmware_version` is below `COMMAND_SUPPORT_SINCE` (1.4.0) — judged per device, since a house can run old and new firmware side by side; OTA URLs must be HTTPS on a host in `OTA_ALLOWED_HOSTS` (empty = all blocked). Heartbeat diagnostics (`booted_at` from `uptime`, `free_heap`, `reset_reason`, `ip`; FARM-FR-006) are type-checked before they are stored (`applyDiagnostics`). The AI node listens on its house's `config/update` for the counting ring the Domain Expert draws (`PUT /devices/camera-nodes/:id/counting-ring`, VISION-FR-018; `mqtt.client#publishHouseCommand`); it is re-sent when the node reconnects, like the ESP32 config. A controller's farm, house and zone come only from its registration (FARM-FR-003c): when its heartbeat arrives on another topic than the registered zone, `recordHeartbeat` sends `config/reassign` with the registered identity on the topic the heartbeat came from. Report 3 moves an offline controller the same way (FARM-FR-007b); `reassignZone` still rejects that (Known debt).

**Roles** (`types/domain.types.ts`, enforced with `requireRole(...)` in `middlewares/auth.middleware.ts`): `ADMIN | FARM_OWNER | DOMAIN_EXPERT | TECHNICIAN`. `DOMAIN_EXPERT` is invited farm-wide by the primary Farm Owner (`POST /farms/:id/members` with `role`). Per Report 3 §2.4 the expert reads dashboards, analytics, alerts, harvests, override history and health reports; edits zone thresholds, fuzzy coefficients, zone detection tuning and the house's bird-count tuning; sets alert verdicts and report conclusions — and cannot drive relays or the speaker, write harvests, acknowledge alerts, edit/delete farms, manage members or create houses/zones. One email = one role. Report 3 §2.4 also gives the Farm Owner device registration, moving and removal (MF-10), keeps Technician and Administrator off zone thresholds, fuzzy coefficients, relay overrides and alert acknowledgement, gives the Technician the structure, devices and device alerts of every farm (never its operational data, FARM-FR-009) and the Administrator no farm, and lets the Farm Owner take the expert's decisions on a farm without one (BR-22); routes that do not follow this yet are listed in Known debt.

**Env vars** (full list in `.env.example`): app (`NODE_ENV`, `PORT`), DB (`MONGODB_URI`, `MONGODB_TEST_URI`), auth (`JWT_ACCESS_SECRET/TTL`, `JWT_REFRESH_SECRET/TTL`), MQTT (`MQTT_BROKER_URL`, `MQTT_USERNAME/PASSWORD`, `MQTT_CA_CERT_PATH`), CORS (`CORS_ORIGIN`), storage (`MINIO_*`, or `STORAGE_DRIVER=local` + `LOCAL_STORAGE_DIR` in dev), devices (`OTA_ALLOWED_HOSTS`), notifications (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME`; `FIREBASE_*`, `SMTP_*`, `ZALO_*` not read yet; nor are `REDIS_URL`, `APP_NAME`), health reports (`HEALTH_REPORT_CRON`, `HEALTH_REPORT_DAYS`), rate limiting (`RATE_LIMIT_WINDOW_MS/MAX`), live stream (`STREAM_TOKEN_SECRET`, `STREAM_AUTH_KEY`, `STREAM_PUBLISH_SECRET` — all empty = video disabled: token endpoint 503, MediaMTX denied).

## Rules

### Layers
- **[Bắt buộc]** Controllers hold no business logic: read `req.params/body/query/user`, call exactly one service function, return `res.json({ success, data, meta? })`. Every handler is wrapped in `asyncHandler` (`utils/asyncHandler.util.ts`); no hand-written `try { … } catch (err) { next(err) }`, no error formatting in the controller.
- **[Bắt buộc]** Only services query the DB, check permissions, publish MQTT and emit socket events. Services throw via `utils/appError.util.ts` (`NotFoundError`, `ForbiddenError`, `ConflictError`, `BadRequestError`, `UnauthorizedError`); only `middlewares/errorHandler.middleware.ts` turns them into HTTP responses.
- **[Bắt buộc]** MQTT handlers (`mqtt/handlers/*.handler.ts`) are thin adapters: parse `topicParts`/`message`, call one service function, never query the DB.
- **[Bắt buộc]** Services emit realtime events only through the `emit*()` helpers in `socket/index.ts`.

### API surface
- **[Bắt buộc]** Every response uses the envelope `{ success, data?, meta?: {page,limit,total}, error?: {code, message} }`; list endpoints paginate with `utils/helpers.util.ts#paginate()` (default 20, max 100).
- **[Bắt buộc]** Every route validates its params/query/body with `express-validator` followed by `validate` (`middlewares/validate.middleware.ts`). Filters that reach a Mongo query are checked as strings first (`.isString()` before `isIn`/`isMongoId`) so `?x[$ne]=` and repeated params cannot become operators or arrays.
- **[Bắt buộc]** Every route that changes state, or reads data a role must not see, has `requireRole(...)` matching the Report 3 §2.4 matrix. A new action never opens to `DOMAIN_EXPERT` if §2.4 says the expert only reads it.
- **[Bắt buộc]** A route added, removed or changed (path, method, params, body, response fields, roles) updates `docs/api/api-spec.yaml` **in the same PR**. Routes stay unprefixed (no `/api/v1`).
- **[Bắt buộc]** Shared enums (`Role`, `AlertType`, `AlertSeverity/Status`, `DeviceStatus`…) in `types/domain.types.ts` change only together with the frontend/mobile copies in the same PR, or the PR says which follow-up PR updates them.

### Data access and permissions
- **[Bắt buộc]** Farm access goes through `utils/farmAccess.util.ts` (`hasFarmAccess`, `isPrimaryOwner`, `assertFarmAccess`, `assertZoneAccess`, `assertZoneInFarm`, `findFarmOrThrow`, `findZoneChainOrThrow`, `listAccessibleFarmIds`/`listAccessibleZoneIds`) — never reimplemented in a service. There is no per-Zone scope; what a role may *do* is decided by `requireRole` on the route.
- **[Bắt buộc]** Soft-deleted farms/harvests stay hidden: query through the models (the `applySoftDeleteScope` hook), delete a farm only via `farm.service#softDeleteFarm`.
- **[Bắt buộc]** `Zone.farm_id` is immutable; zone→farm lookups use it, not `House`.
- **[Bắt buộc]** Sensitive state changes (users, roles, members, thresholds, tuning, overrides, system settings, remote device commands) write an audit row with `logAction()`.

### Device, MQTT and control
- **[Bắt buộc]** A command meant for one device on a zone topic (`relay/command`, `audio/command`, `config/reassign`, a `config/update` carrying speaker settings or RESTART/OTA) carries `deviceId: node.device_id`.
- **[Bắt buộc]** `utils/fuzzyModel.util.ts` mirrors `firmware/src/pid/FuzzyControl.cpp`; a change to one is made to the other in the same PR, with the shared test cases updated.
- **[Bắt buộc]** Runtime device parameters (thresholds, fuzzy coefficients, detection tuning) go out through `buildDeviceConfig`/`config/update`, validated against the same ranges the firmware clamps to.
- **[Bắt buộc]** Inferred alert types stay MEDIUM/LOW, so they are never sent again by ALERT-FR-015; alerts go through `createAlert()`/`ingestDeviceAlert`.

### Scope and constants
- **[Bắt buộc]** Nothing new for what Report 3 §8 puts out of scope (Marketplace/Buyer, Farm Operator and zone scope, predator detection, heating, Zalo/SMS, NH3/CO2 driving the fan).
- **[Bắt buộc]** No threshold, limit or behaviour without a source (Report 3, the Domain Expert, a cited reference). An engineering constant that has to be picked anyway is added to Report 3 §4.5 (engineering constants, A-4) in the same PR.
- **[Nên]** Account and Admin code are supporting flows (Report 3 §2.2 SF-03, priority S): keep them working, do not extend them. Tickets, SLA, routing, KPIs, maintenance schedules and Technician regions are out of scope (Report 3 §8, BM03 row 9): the ticket module is gone from the backend, regions are still to remove; escalation became a repeated notification (ALERT-FR-015) and relay wear `MAINTENANCE_DUE` (ALERT-FR-016). Device setup is not one of them: it is main flow MF-10, owned by the Farm Owner.

### Quality
- **[Bắt buộc]** No `console.*` outside `src/scripts/` (ESLint `no-console`); log through `utils/logger.util.ts`. The two dev OTP/reset-code prints in `auth.service.ts` (with `eslint-disable`) are the only exception and are listed in Known debt. No unused vars (prefix `_` when a signature needs them).
- **[Bắt buộc]** No `any`/`as any`/`@ts-ignore` in new code; unknown input is `unknown` and narrowed.
- **[Bắt buộc]** New or changed service logic has Jest tests (unit, or integration with `mongodb-memory-server`) covering the main path and the permission/validation failures; a bug fix adds a test that fails without it.
- **[Bắt buộc]** Migrations in `src/scripts/migrate-*.script.ts` are idempotent (safe to run twice) and get an `npm run migrate:*` script plus a line in this file's Commands.
- **[Bắt buộc]** A new env var is added to `.env.example` with a comment, and read with a safe default or a clear startup error.
- **[Bắt buộc]** File naming `<resource>.<layer>.ts` with the layer spelled out (`.service`, `.controller`, `.route`, `.model`, `.middleware`, `.util`, `.handler`, `.job`, `.script`) — never `farmService.ts`.
- **[Nên]** Test files: a unit test mirrors its source file (`tests/unit/<src folder>/<file>.test.ts`, e.g. `tests/unit/utils/thresholds.util.test.ts`); an integration test is named after the feature it covers in camelCase (`tests/integration/<feature>.test.ts`, e.g. `alertLifecycle.test.ts`) — never after a PR or review round. Shared fixtures go in `tests/helpers/` (`ownerFarm.ts`: in-memory DB + a seeded farm); `jest.mock` calls stay in each test file.
- **[Nên]** Comments explain *why* (business reason, FR code from Report 3), not what the code does.
