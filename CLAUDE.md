# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It holds what every module shares; each module's own `CLAUDE.md` holds its architecture and rules and is loaded when you work in that folder.

## Project overview

SwiftletCare — IoT monitoring + automation system for swiftlet (yến) houses (KLTN/thesis project, FA26, FPT University). Modules, each independent (no root `package.json`/workspace):

- `firmware/` — ESP32 (PlatformIO): RS485 sensors, fuzzy relay control, MQTT, lullaby speaker. → `firmware/CLAUDE.md`
- `backend/` — Node.js + Express + TypeScript + MongoDB + MQTT (EMQX) + Socket.io. → `backend/CLAUDE.md`
- `frontend/` — React 18 + Vite + TailwindCSS web dashboard/PWA. → `frontend/CLAUDE.md`, rules in `frontend/FE_Design_Claude.md`
- `mobile/` — Expo (Router, file-based routes) + React Native app, talks to the same backend API. → "Mobile" below
- `ai-pipeline/` — YOLO26n (ONNX Runtime) + ByteTrack bird counting on an AI node — the team's spare PC at a member's home, reading the camera over the Internet (Report 4 D5; plan in `docs/bird-counting-plan.md`). **Runs on clips and the real camera with a temporary COCO model; not deployed:** it tracks, counts, publishes session counts, 5-minute buckets and heartbeats over MQTT and pushes the annotated stream to MediaMTX (PR #89, merged into `develop` by PR #95), but there is no trained swiftlet model yet (the COCO model finds no bird in infrared images); ONNX weights are never committed. → "AI pipeline" below
- `docs/` — `docs/reports/` holds the Review 2 documents: registration form v3 + BM03, Reports 1 and 2, **Report 3 `report3-srs.md` (requirements)**, **Report 4 `report4-sdd.md` (design)**, Report 5 (tests, generated from `report5/tc.py`), Project Tracking, the Design Brief (BM01) and `README.md` (report status, code gaps). Word forms are generated from the Markdown by `docs/reports/tools/`. Staging: `docs/deploy/staging.md`. `docs/api/api-spec.yaml` is the OpenAPI 3.0 **source of truth** for the API contract; the backend reads it at boot and serves Swagger UI at `/api-docs`. Routes are unprefixed (no `/api/v1`). `docs/database/init.mongo.js` is the database script generated from the Mongoose models (`npm run db:script` in `backend/`).

**Requirements and design: Report 3 and Report 4.** `docs/reports/report3-srs.md` (Report 3, SRS 3.1.0, English) is the requirements baseline and `docs/reports/report4-sdd.md` (Report 4) is the design; they win over every other text, including `SwiftletCare_SRS.md`, which is now an internal Vietnamese record (scope history, detailed flows) — never add requirements there. FR codes are the same in both. Report 4 (SDD 1.1.0) describes the final design, without implementation status. Where the code still differs from Report 3 or Report 4, the gap is listed once, in `docs/reports/project-tracking.md` §6 (G-01…G-19; work steps in `docs/reports/todo-review2.md`): check it before assuming a feature is done, and update that row in the PR that closes a gap.

**Scope (Report 3 §1.2, §2.2, §8).** One installation serves one owner of swiftlet houses and that owner's farms: the Administrator creates the Farm Owner's and Technicians' accounts, co-owners and the Domain Expert join by invitation, and there is no public sign-up (BM03 row 10, gap G-02). Reviews judge the system against the proposed final registration form v3 (`docs/reports/registration-v3.md`, Word file in `docs/reports/registration/`) and its Record of Changes (`docs/reports/bm03-record-of-changes.md`). **`backend/` and `firmware/` (1.4.0) follow the Review 1 scope**, with the Report 3 gaps above; `frontend/`, `mobile/` and `ai-pipeline/` still follow v1.24.0. In short:

- **Main flows MF-01…11 are the automated system** (Report 3 §2.2): fuzzy microclimate control, offline operation and recovery, self-diagnosis and alerts, early warning by forecast, bird counting with an annotated live stream, abnormal noise, expert validation and tuning, manual override, device setup by the Farm Owner, and the daily health assessment with periodic reports. Supporting flows SF-02 (remote device maintenance by the Technician), SF-03 (accounts) and SF-04 (harvest logging) are priority S — keep them working, don't extend them.
- **Multi-modal health = one daily status per house (MF-11):** environment, air quality, flock return rate and abnormal noise are each rated against the house's levels and combined by agreement between sources (BR-28…30, rain as context from a weather API), with reasons; daily/weekly/monthly reports export to PDF/CSV; the Farm Owner and the expert rate each day from their own observation before seeing the status (BR-31), and the agreement is measured (NFR-14). The status is an indicator, not a diagnosis.
- **Device setup is the Farm Owner's (MF-10):** in the mobile app, scan the label QR of a controller (device ID + activation key, FARM-FR-010) and the QR code of its floor (FARM-FR-011). Nothing about the farm is typed on the device: the AP-mode page takes only Wi-Fi and the broker address, and the farm, house and zone stay in the backend: the controller only receives its zone's configuration (FARM-FR-003c, BR-26/27; until G-07 the code still corrects the topic with `config/reassign`). Cameras (AI nodes) are registered to a house within MF-06 (FARM-FR-004). A Technician may do the same steps on any farm.
- **Domain Expert** (role `DOMAIN_EXPERT`, whole farm, no `zone_ids`): reads operations; confirms or rejects inferred alerts (a rejected one becomes `DISMISSED`); edits zone thresholds and fuzzy coefficients, reviews the Farm Owner's own changes (EXPERT-FR-010) and is the only one who applies a coefficient suggestion (EXPERT-FR-011); tunes five per-Zone detection parameters and the per-House return-rate drop (EXPERT-FR-008), the counting ring and the counting schedule; writes conclusions. No relay control, harvest writes or alert acknowledgement. The Farm Owner is notified of every expert decision (EXPERT-FR-009); on a farm without an expert the Farm Owner takes those decisions (BR-22). Thresholds and fuzzy coefficients belong to the farm: Technician and Administrator never edit them, and the Administrator's system defaults are copied into a zone only at creation or reset (ENV-FR-007/020). Permissions per role: Report 3 §2.4.
- **No platform functions (Report 3 §8, BM03 row 9):** no maintenance tickets, ticket chat, SLA, ticket routing or queues, Technician regions or KPIs, maintenance schedules, and the Administrator does not create or manage farms. The **Technician** is the technical role: sees the houses, zones, devices and device alerts of every farm (never its environmental data), sets up/moves/removes devices, sends RESTART, configuration push and OTA (FARM-FR-009, 013); never switches relays, edits thresholds or coefficients, or acknowledges alerts; every device action is audited and notified to the Farm Owners. An alert nobody acknowledges is sent again (ALERT-FR-015) and pump/fan wear raises `MAINTENANCE_DUE` (ALERT-FR-016) instead of creating tickets. Ticket, SLA and region code was removed (PR #104–#105 backend, PR #106 web/mobile); never bring it back.
- **Out of scope (Report 3 §8):** Buyer + Marketplace (harvest logging stays), predator detection, heating, Zalo/SMS. Out-of-app alerts go through **both** a Telegram bot (ALERT-FR-013) and FCM push (ALERT-FR-002). Vision is one class (`swiftlet`) on an AI node that is a desktop PC at a member's home reading the camera over the Internet (staging: Report 4 §3.4, §11, `docs/deploy/staging.md`), not a Raspberry Pi; cameras, bird counts and their alerts belong to the House (Report 3 §2.8).
- **NH3/CO2 are monitor-and-alert only** — they never drive the fan. `BIRD_PANIC` became `NOISE_ANOMALY`, an inferred signal shown with bird counts and validated by the expert.
- **Never invent a threshold or behaviour without a source**; if none is found, downgrade the claim (alert-only, "set by the Domain Expert"). An engineering constant that had to be picked anyway is added to Report 3 §4.5 (assumption A-4) in the same PR.

Known repo quirks:
- `docker compose` runs no Mongo init script: the backend logs in as the root user from `docker-compose.yml`, and collections/indexes come from Mongoose, `npm run seed` and `npm run migrate:*`. `docs/database/init.mongo.js` (Report 4 §6.5) is run by hand with `mongosh` when a database must be created from scratch. A machine that ran an older compose file may hold an empty `docs/db/` folder (untracked) — safe to delete.
- Docs live under `docs/` (map: `docs/FOLDER_STRUCTURE.md`); only the old `SwiftletCare_SRS.md` stays at the repo root. `docs/hardware/` has `BOM.md` and `components-guide.md` but no circuit diagram or prototype photos; `docs/test-reports/` only has a `.gitkeep`.

### Cross-module rules

These bind more than one module, so a PR on either side must respect them:

- **API contract.** `docs/api/api-spec.yaml` describes every route; a route change updates it in the same PR, and frontend/mobile calls follow it.
- **Shared enums.** `backend/src/types/domain.types.ts`, `frontend/src/types/` and `mobile/src/types/` keep the same enum values (`Role`, `DeviceStatus`, `AlertSeverity/Type/Status`…). They are not a generated mirror — renaming on one side changes nothing on the other. Since gap G-01 (PR #113, 29/10/2026) they follow Report 3 3.1.0: `DISMISSED` in `AlertStatus`; `CONFIG_MISMATCH`, `ACTUATOR_FAULT`, `MISTING_INEFFECTIVE` (was `PUMP_DRY`) and `UNEXPECTED_RESTART` (was `POWER_OUTAGE`, with `reset_reason`) in `AlertType`; no `PREDATOR_DETECTED`, Zalo/SMS preferences, `heating` relay field, device states `ERROR`/`DEGRADED` or harvest state `ARCHIVED`. The backend still accepts the old names from older firmware (`ALERT_TYPE_ALIAS`); `npm run migrate:alert-types` converts stored data. Never bring an old value back.
- **MQTT.** Target design (Report 4 D3, §7.2): one topic tree and one broker credential per device, `swiftletcare/dev/{deviceId}/telemetry|telemetry/buffered|heartbeat|relay/status|alert|vision/bird-count|vision/alert` up, `…/config` (retained, versioned) and `…/cmd` (envelope `commandId`, `type`, `issuedAt`) down; QoS 1 for everything but live telemetry and heartbeat; EMQX authenticates devices through `/internal/mqtt-auth` and lets a device reach only its own tree; the backend keeps farm, house and zone, so `config/reassign` disappears; the ESP32 moves from PubSubClient to `esp-mqtt` over TLS. This is gap G-07 — firmware, backend and AI node change in one PR, and the paragraph below describes the code until then. Current code: ESP32 topics are `swiftletcare/{farmId}/{houseId}/{zoneId}/...`; the bird-counting AI node publishes per house, `swiftletcare/{farmId}/{houseId}/heartbeat|vision/bird-count|vision/alert` (the camera watches the entrance of the whole house, so cameras, bird counts and their alerts belong to the House, not a Zone — Report 3 §2.8). Real MongoDB ObjectIds. A controller's farm, house and zone come only from its registration: the backend sends `config/reassign` when a heartbeat arrives on another topic than the registered zone (FARM-FR-003c), so no identity field goes back onto the AP-mode page. Backend ingestion keys off `deviceId` inside the payload, not topic segments. Any command meant for one device on a zone topic (`relay/command`, `audio/command`, `config/reassign`, a `config/update` carrying speaker settings or RESTART/OTA) carries `deviceId`; firmware drops commands addressed to another device and applies ones without it (zone-wide thresholds).
- **Fuzzy model.** `firmware/src/pid/FuzzyControl.cpp` and `backend/src/utils/fuzzyModel.util.ts` change together, with the shared test cases.
- **Runtime parameters** (thresholds, fuzzy coefficients, detection tuning) use the same names and ranges in the backend validator and the firmware clamp.

## Commands

Each module's own file lists its full command set. The ones you need most:

```bash
docker compose up -d mongodb emqx          # infra (add minio, redis if needed)
cd backend  && npm run dev                 # API on :3000 — dev MQTT must be mqtt://localhost:1883 (EMQX self-signs 8883)
cd frontend && npm run dev                 # http://localhost:5173, proxies /api and /socket.io to :3000
cd firmware && pio test -e native          # firmware host-side unit tests
```

Mobile (`mobile/`): Expo app pointing at `localhost:3000` by default (`src/constants/apiEndpoints.ts`); scripts `start`/`android`/`ios`/`prebuild`, `build:dev|preview|prod` (EAS profiles in `eas.json`), `lint`, `test` (jest), `typecheck`.

## Mobile (`mobile/`)

All code in `mobile/src/` (assets stay in `mobile/assets/`). Expo Router (file-based routing) under `mobile/src/app/`: `(auth)` group (login, forgot-password, verify-code, reset-password; no public sign-up) and `(tabs)` group (dashboard/alerts/analytics/farms/profile, plus placeholder menu-1..2; the tabs each role sees come from `src/constants/roleTabs.ts`), plus detail routes `farm/[farmId]`, `zone/[zoneId]`, `device/[deviceId]`, `alert/[alertId]`, `livestream/[zoneId]`. Supporting code in `src/components/`, `config/`, `constants/`, `hooks/<domain>/`, `services/{api,socket,notification}/`, `stores/`, `types/`, `utils/`, each split by business domain (map and naming: `mobile/MOBILE_GUIDE.md` §2, §3.8). Talks to the **same backend**, unprefixed routes (`src/constants/apiEndpoints.ts`'s `ENDPOINTS` map follows `docs/api/api-spec.yaml`). React Query + Zustand + axios + socket.io-client, same overall pattern as the web frontend; storage via `react-native-mmkv`, charts via `victory-native`. Most screens are stubs. Enums match the backend since PR #106 (`DOMAIN_EXPERT`, `NOISE_ANOMALY`, no ticket types); still left from v1.24.0: the `zalo`/`sms` notification fields (not shown on screen) and no FCM registration — only remove or replace these, never extend them. Report 3 makes mobile carry two main-flow pieces: FCM token registration (ALERT-FR-002) and device setup by QR scan (`expo-camera`, MF-10).

## AI pipeline (`ai-pipeline/`) — not deployed

`src/stream.py` (latest-frame RTSP reader, sessions in Vietnam time, MQTT, MJPEG preview, push to MediaMTX) → `pipeline.py` (mask the camera clock → two overlapping tiles → `inference.py` YOLO via ONNX Runtime, YOLO26 and YOLOv8/11 outputs → `sv.ByteTrack`) → `counting.py` (`RingCounter`: a closed ring around the entrance hole, plus extrapolation for birds that cross the hole in 1-2 blurred frames; `BucketClock` for 5-minute counts). Every bird is tracked over the whole frame, not only near the hole (plan §19.8). The AI node publishes per house on `swiftletcare/{farmId}/{houseId}/heartbeat|vision/bird-count` and takes the ring the Domain Expert draws from `config/update` (`remote_config.py`, VISION-FR-018). The backend side is ready: `vision/bird-count` → `backend/src/services/birdCount.service.ts` (session records, 5-minute buckets, `LOW_RETURN_RATE` job), the AI node's heartbeat/`EDGE_AI_DEGRADED` (plan §8) and live-stream access for MediaMTX (`stream.service.ts`, §8.6). Only class `swiftlet`; the COCO model does not find swiftlets in the IR frames, so `tools/track_clip.py --detector motion` and `tools/extract_frames.py` (draft labels for Roboflow) stand in until a model is trained (plan §7). Clips, frames and datasets live on `D:\SwiftletCare\`, recorded daily by `tools/record_session.ps1`. `config/config.yaml` session windows are only defaults: Report 3 has the backend compute sessions from 5-minute buckets per the house's counting schedule (VISION-FR-008/019, not built yet); one class, `swiftlet` — predator detection may only be removed, never extended. `{house}/vision/alert` carries only `EDGE_AI_DEGRADED`.

## Conventions

- Commit messages follow Conventional Commits with a project-specific `type`/`scope` enum enforced by commitlint (`.commitlintrc.json`). CI (`.github/workflows/ci.yml`) validates them via `wagoid/commitlint-github-action`, runs a gitleaks secret scan, and — only for the modules a PR touches (`dorny/paths-filter`) — runs **backend** `npm run lint` · `build:check` · `npm test` (integration tests use `mongodb-memory-server`), **frontend** `npm run lint` · `tsc --noEmit` · `vitest run` · `npm run build`, **firmware** `pio test -e native`, **mobile** `npm run lint` · `typecheck` · `jest --passWithNoTests`, **ai-pipeline** `pytest`. Run the same commands locally before pushing.
- Tests are written by whoever builds the feature, in the same PR — not left for someone else later. How much is required is set per module (backend: [Bắt buộc] for new or changed service logic; frontend and mobile: [Nên] for pure logic; firmware: [Bắt buộc] for control/filter/detection logic).
- Both `backend` and `frontend` use the `@/*` → `src/*` path alias.

## Working with Claude

- Reply to the user in Vietnamese.
- **Who does what.** `docs/reports/todo-review2.md` §0 is the team's work split: each member's role, the files each one owns, one branch per gap and the order of work (steps before the `review-2` tag: §0.3). Before writing code, find which member you work for — match `git config user.name` with the GitHub handles in `docs/reports/project-tracking.md` §2, or ask — and take only that member's steps. `backend/` is written only by Bảo and Kiệt; never edit a file another member owns (§0.2), say what is needed instead. A step whose dependency (§0.2, rule 4) is not merged on `develop` yet waits.
- Review a PR with `/review-pr <PR number>` (`.claude/commands/review-pr.md`). That file is the single review procedure: the "PR auto-review" routine on claude.ai reads it too, so change review behaviour there, not in the routine. It judges each module by its own rules plus the Report 3 scope and the cross-module rules, and posts a COMMENT-only review on the owner's own PRs. A PR-triggered routine run is checked out at the PR's head, so the routine must read `review-pr.md` from the PR's base branch (`git show origin/<base>:.claude/commands/review-pr.md`), never from the checkout — otherwise a PR could change the rules it is reviewed by. Routine runs have no built-in `/code-review`; the command then falls back to a find-then-verify review with `Agent` subagents. When reviewing, read code and diffs only — never run `npm install`/`npm ci`, builds or test suites.
- Keep `review-pr.md` lean: before adding a step or rule to it, name a real bug or rule break that the new step would have caught and the current text would not. Prefer a test or a CI check over a new review instruction — CI checks every PR the same way, a prompt does not.
- Commits and PRs carry no Claude attribution (`.claude/settings.json` sets `attribution` to empty) — don't add `Co-Authored-By`, session links or similar lines by hand either.
